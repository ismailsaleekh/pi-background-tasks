# PR 25: fix(core): stop retrying terminal publication into a closed EventBus
Author: erikdarlingdata (FIRST_TIME_CONTRIBUTOR)
State: open; Created: 2026-09-19T16:05:51Z; Updated: 2026-09-19T16:06:48Z
URL: https://github.com/ismailsaleekh/pi-background-tasks/pull/25

Fixes #24.

## The bug

`handleTerminalPublishFailure` reschedules every failed terminal publish after 100ms, gated only on `!task.terminalPublished`. That flag can never become true once the EventBus service is closed, because `publishTerminal` throws before it is set (`tryPublishTerminalNow`) — so the failure handler re-arms itself indefinitely:

```
[background-tasks] terminal publication failed for bda5adc28: Error: pi-background-tasks EventBus service is closed
    at InstalledBackgroundTaskExtensionService.publishTerminal (src/core/extension-api.ts:423:28)
    at BackgroundTaskRegistry.publishTerminal [as publishTerminalSnapshot] (src/extension.ts:222:20)
    at BackgroundTaskRegistry.tryPublishTerminalNow (src/core/registry.ts:2265:12)
    at BackgroundTaskRegistry.publishTerminal (src/core/registry.ts:2246:12)
    at Timeout._onTimeout (src/core/registry.ts:2285:14)
```

The bottom frame is the retry this handler scheduled, so the trace is the loop rather than a single failure. In practice that is a full stack trace roughly ten times a second, written under a live TUI, which makes the terminal unusable.

Two details make it worse than a noisy log:

- `unref()` stops the timer from holding the process open at exit, but the pi process is long-lived, so it doesn't bound anything.
- The timer belongs to the **previous activation's** registry, so `/reload` cannot reach it. The flood continues until the process is killed.

The closed-bus state is reachable in ordinary use: `session_shutdown` closes the service in its `finally` (`src/extension.ts:513`) while the same handler drives running tasks terminal via `stopTask`, and a gated publish — fusion tasks build a `terminalPublicationGate` (`src/fusion-extension.ts:836`) — can resolve after that close.

## The fix

Treat a closed bus as terminal: log once and give up, mirroring the `shuttingDown` short-circuit `notifyCompletion` already has twelve lines below. The guard fires on either `this.shuttingDown` or an `EventBus service is closed` message.

Setting `task.terminalPublished` is what actually ends the loop, since every publish path checks it — it means "no further attempts", not "delivered". The comment in the diff says so explicitly, so it doesn't read as a false success later.

Transient failures are untouched and keep retrying; the pre-existing `keeps failed terminal EventBus delivery loud and retriable` test still pins that path and still passes (its error message doesn't match the closed-bus signature and `shuttingDown` is false, so it falls through to the existing retry).

## Tests

Two regression tests added to `tests/unit/registry.test.ts`, one per guard arm, each asserting no re-arm after 350ms — comfortably past the 100ms retry interval:

- `stops retrying terminal publication once the EventBus is closed` — asserts exactly one attempt, `terminalPublished === true`, handle cleared, `terminalPublishInFlight === false`
- `stops retrying terminal publication while shutting down` — a generic error raised after `setShuttingDown(true)`, asserting one attempt and no pending handle

Verification on this branch:

- `npx tsx --test tests/unit/registry.test.ts` — 32/32 pass

## Alternatives, if you'd prefer a different shape

Both were mentioned in #24 and I'm glad to rework this into either:

- **Bounded retries for all failure modes** — an attempt counter on the task, so no persistent error can loop indefinitely, rather than special-casing this one.
- **Cancel pending retry handles at shutdown** — clear each task's `terminalPublishRetryHandle` alongside `eventService.close()`, so a queued retry can't fire into a closed bus at all.

They're complementary to this change rather than substitutes; this one fixes the observed flood with the smallest diff and no new task fields.
