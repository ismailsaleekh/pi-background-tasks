# Issue 14: Anthropic cache lineage guard bricks the session instead of resetting
Author: Ely1985 (NONE)
State: open; Created: 2026-09-05T08:10:29Z; Updated: 2026-09-08T19:29:44Z
URL: https://github.com/ismailsaleekh/pi-background-tasks/issues/14

**Package:** pi-background-tasks 2.5.0
**File:** `src/core/anthropic-attribution.ts`, `prepareAnthropicLineageDetails` (~line 2072)

## Problem

When the recorded lineage prefix no longer matches the outgoing message history
(e.g. after interrupting the agent mid-stream, or after an extension/context
reload mutates the history), `prepareAnthropicLineageDetails` throws:

```text
Error: Anthropic cache lineage diverged before transport: message history is not append-only
```

Because the divergence is persistent (the recorded lineage diagnostic lives on
the last assistant message and the mismatched prefix never heals on its own),
**every subsequent request on that session fails before transport**. The user
cannot send anything anymore — including `/compact`, which itself needs a model
call. The only escape hatches are `/tree`-pruning past the offending assistant
message or abandoning the session.

## Reproduction

1. Run a session on an Anthropic (Claude Code OAuth) route with the extension loaded.
2. Interrupt the agent mid-stream so a partial assistant/tool message is truncated/removed from the persisted history (a mid-session "Reloaded keybindings, extensions, skills, prompts, themes, and context files" reload can also contribute).
3. Send any new message → the error above, repeatedly, forever.

## Expected behavior

Lineage divergence should degrade gracefully: reset `previous = undefined`
(accepting a one-off cache miss for that request) and optionally emit a
warning/diagnostic, exactly as the code already does when a new compaction
boundary is declared or when `cache_retention` changes. Hard-failing is
appropriate for integrity-critical invariants, but here the failure mode is a
permanently unusable session with no user-visible recovery path.

## Suggested fix

In `prepareAnthropicLineageDetails`, replace the two `throw new Error(...)`
branches (`!prefixStillExists` and `cache_profile_sha256` mismatch) with
`previous = undefined` plus a warning, e.g.:

```ts
if (!prefixStillExists) {
  console.warn('anthropic cache lineage diverged (history not append-only); resetting lineage');
  previous = undefined;
} else if (previous.cache_profile_sha256 !== profileSha256) {
  console.warn('anthropic cache lineage diverged (profile changed); resetting lineage');
  previous = undefined;
} else if (previous.cache_retention !== cacheRetention) {
  previous = undefined;
}
```

Locally patching this restores the session immediately with no observable
downside beyond the expected cache miss.

## Comment by joelleibow — 2026-09-08T19:29:44Z
Confirming this on pi-background-tasks 2.5.0 with a plainer trigger than a mid-stream interrupt: it reproduces on an ordinary `/resume` or `/reload` of an Anthropic OAuth session, with no interruption involved.

The mechanism is exactly as described. On resume/reload pi reconstructs `context.messages` from the session JSONL, and the reconstructed prompt prefix is not byte-identical to what `appendLineageDiagnostic` recorded on the last successful assistant message — most reliably because prior assistant thinking blocks are dropped/re-serialized on reload. `prepareAnthropicLineageDetails` then hits `!prefixStillExists` and throws before transport.

It's permanent per the reporter's analysis because `latestLineageForTarget` skips `stopReason: 'error'` messages, so the failed turn never re-anchors — every retry compares against the same stale fingerprint and re-throws. The only in-session escape is `/tree`-pruning past the offending assistant message.

Two details worth folding into the fix:

1. The graceful-reset (`previous = undefined` + warn) is the right call, but note the reload trigger means it will fire on the **first turn after every resume/reload** of any non-trivial Anthropic session, not just after an interrupt — so silently accepting the one-off cache miss (not a warn per turn) is the better UX.
2. The provider override is registered ambiently in the main session via the package manifest, but child processes (fusion/delegate/attested) load `anthropic-attribution` by explicit path. So a viable stopgap for affected users is filtering `extensions/anthropic-attribution.ts` out of ambient loading in `settings.json` while keeping it for children — which is what I've done locally. Worth documenting until the guard is softened.
