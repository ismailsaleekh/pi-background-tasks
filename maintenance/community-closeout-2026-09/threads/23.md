# PR 23: fix(pi-launch): locate the Pi manifest from the running host script on Windows
Author: boggylp (FIRST_TIME_CONTRIBUTOR)
State: open; Created: 2026-09-18T12:28:12Z; Updated: 2026-09-18T12:31:25Z
URL: https://github.com/ismailsaleekh/pi-background-tasks/pull/23

🤖 On Windows, `bg_delegate`, the Fusion tools, and `bg_run_pi_attested` fail before spawning when Pi is installed globally and this package sits in Pi's extension prefix:

```
pi_executable_resolution_failed: package manifest resolve failed for @earendil-works/pi-coding-agent/package.json: Cannot find module '@earendil-works/pi-coding-agent/package.json'
Require stack:
- C:\Users\<user>\.pi\agent\npm\node_modules\pi-background-tasks\src\core\pi-launch.ts; package entry resolve failed: Cannot find module '@earendil-works/pi-coding-agent'
```

`resolvePiLaunch()` finds the Pi manifest through `createRequire(import.meta.url)`, which walks `node_modules` upward from `~/.pi/agent/npm`. A global Pi lives under `%APPDATA%\npm\node_modules`, off that path. Pi's extension loader aliases `@earendil-works/pi-coding-agent` for extension imports, so the package is present at runtime and invisible only to this lookup. This is the shape `pi install npm:pi-background-tasks` produces on a machine that followed Pi's documented `npm install -g`.

The process that loads this extension is Pi, so its own entry script (`process.argv[1]`) sits inside the Pi package. When both module lookups fail, resolution walks up from that script to the nearest `package.json` that carries a `name` and accepts it only when the name is `@earendil-works/pi-coding-agent`. Nameless sub-manifests such as a `dist/package.json` type marker are stepped over. The result feeds the existing route unchanged: `bin.pi`, realpath, package-root containment, regular-file and extension checks. No PATH shim is consulted. When the nearest named manifest belongs to another package, or none exists, resolution fails closed and the error names all three attempts.

`PiLaunchDependencies` gains `resolveModule` and `hostScript` so the fallback order and the combined error are asserted against fakes rather than the test host's own `node_modules`.

Related: #9 extends the POSIX branch with a host-self launch. This change covers the Windows branch and keeps the manifest-validated route, so the two are independent.

## Verification

- `npm run typecheck`, `npm run test:unit` (pi-launch 11/11, four new cases), `npm run docs:generate` and `npm run docs:verify` deterministic OK; remaining default-gate lanes run individually.
- Negative control: with the manifest `name` check inverted, the new tests fail.
- On the affected machine (Windows 11 arm64, Pi 0.85.1 global, package 2.5.0 in the extension prefix), the host-script walk resolves `%APPDATA%\npm\node_modules\@earendil-works\pi-coding-agent\package.json` and yields the `package-node-cli` launch through `process.execPath`.
- On this Windows host, `main` already fails `test:type-safety` (`src/core/anthropic-attribution.ts:83` and `:1493`), six `test:sdk` delegate cases, and two `test:package` cases. The failures are identical with and without this change, so the chained `npm run test` stops at type-safety either way. `test:rpc`, `test:component`, and `test:hook-contract` pass.
