# Issue 24: Terminal publication retries forever after the EventBus closes: unbounded 100ms stack-trace flood for the life of the process
Author: erikdarlingdata (NONE)
State: open; Created: 2026-09-19T15:56:20Z; Updated: 2026-09-19T15:56:20Z
URL: https://github.com/ismailsaleekh/pi-background-tasks/issues/24

## Summary

When a task's terminal publish happens at/after `session_shutdown`, `publishTerminal` throws `EventBus service is closed` — and `handleTerminalPublishFailure` responds by scheduling another attempt in 100ms, with **no closed/shutting-down guard and no attempt cap**. The retry throws identically, so the failure handler re-arms itself forever: roughly **10 full stack traces per second, for the life of the pi process**, written straight to the terminal underneath a running TUI.

Practical effect: the terminal becomes unusable (the flood fights the TUI for stdout) and `/reload` can't fix it, because the timer belongs to the *previous* activation's registry — a fresh session in the same process has no handle on it. The only escape is killing the pi process.

## Why it never stops (v2.5.0 line numbers)

`handleTerminalPublishFailure` (`src/core/registry.ts:2279`):

```ts
private handleTerminalPublishFailure(task: BgTask, error: unknown): void {
  this.logger.error(`[background-tasks] terminal publication failed for ${task.id}:`, error);
  task.terminalPublishInFlight = false;
  if (!task.terminalPublished && task.terminalPublishRetryHandle === undefined) {
    task.terminalPublishRetryHandle = setTimeout(() => {
      task.terminalPublishRetryHandle = undefined;
      this.publishTerminal(task);      // 2285 -> throws again -> back here
    }, 100);
    task.terminalPublishRetryHandle.unref();
  }
}
```

The retry condition is only `!task.terminalPublished`, which can never become true once the bus is closed — `publishTerminal` throws before `terminalPublished = true` is reached (`tryPublishTerminalNow`, `:2265`). So the loop is unconditional.

Contributing details:

- **No guard.** `notifyCompletion` twelve lines below (`:2292`) *does* short-circuit on `this.shuttingDown`. The publish path just never got the same check — which is what makes this look like an oversight rather than a design choice.
- **`unref()` doesn't bound it.** It keeps the timer from holding the process open at exit, but the pi process is long-lived, so it has no effect on the flood.
- **Nothing cancels pending retries at shutdown.** `eventService.close()` (`src/extension.ts:513`) doesn't clear `terminalPublishRetryHandle`, and the retry closure keeps the orphaned registry reachable, so it outlives the session that created it.
- **Unrecoverable by construction.** Once the service is closed there is no consumer that could ever receive the snapshot, so every retry is guaranteed to fail — the work being retried cannot succeed.

## How the closed-bus state is reached

`session_shutdown` (`src/extension.ts:486`) flags `shuttingDown`, kills every running task, then closes the service in its `finally` (`:513`). Two paths reach a publish at/after that close:

1. The shutdown handler's own `stopTask(...)` calls (`:494`–`:504`) drive tasks terminal, and each terminal publish races the `close()` in the same `finally`.
2. A **gated** publish resolves after the close — fusion tasks build a `terminalPublicationGate` (`src/fusion-extension.ts:836`), and `publishTerminalWhenReady` awaits it before publishing.

I hit this in ordinary use with background/fusion tasks alive across `/reload`; I haven't isolated which path fired in the captured trace, and the fix is the same either way. Related lifecycle context in #6, which documents tasks being killed by `/reload`.

## Repro sketch

1. Start pi, launch a background or `fusion_*` task.
2. While it's still running, trigger session replacement (`/reload`, `/new`, `/resume`, or quit).
3. If a terminal publish lands after the bus closes, the terminal begins flooding and does not stop until the process is killed.

It is a race, so it doesn't fire on every attempt — which matches the "sometimes goes glitchy" reports.

## Proposed fix

Treat a closed bus as terminal: log once, stop. This is the patch I'm running locally (against 2.5.0) and it ends the flood:

```diff
   private handleTerminalPublishFailure(task: BgTask, error: unknown): void {
-    this.logger.error(`[background-tasks] terminal publication failed for ${task.id}:`, error);
     task.terminalPublishInFlight = false;
+    // A closed EventBus is unrecoverable: no consumer can ever receive this
+    // snapshot, so retrying is an unbounded 100ms log loop for the life of the
+    // process. `terminalPublished` is the flag every publish path checks, so
+    // setting it is what actually stops the loop -- it means "no further
+    // attempts", not "delivered".
+    const message = error instanceof Error ? error.message : String(error);
+    if (this.shuttingDown || message.includes('EventBus service is closed')) {
+      this.logger.error(
+        `[background-tasks] terminal publication abandoned for ${task.id} (event bus closed); not retrying.`,
+      );
+      task.terminalPublished = true;
+      if (task.terminalPublishRetryHandle) {
+        clearTimeout(task.terminalPublishRetryHandle);
+        task.terminalPublishRetryHandle = undefined;
+      }
+      return;
+    }
+    this.logger.error(`[background-tasks] terminal publication failed for ${task.id}:`, error);
     if (!task.terminalPublished && task.terminalPublishRetryHandle === undefined) {
       task.terminalPublishRetryHandle = setTimeout(() => {
         task.terminalPublishRetryHandle = undefined;
         this.publishTerminal(task);
       }, 100);
       task.terminalPublishRetryHandle.unref();
     }
   }
```

Two hardening options worth considering alongside it, whichever you prefer:

- **Bounded retries for every failure mode**, not just this one — an attempt counter on the task so no persistent error can loop indefinitely.
- **Cancel pending retry handles during shutdown**, so a queued retry can't fire into a closed bus at all (clearing `terminalPublishRetryHandle` for each task before/alongside `eventService.close()`).

Happy to open a PR with whichever shape you'd rather have.
