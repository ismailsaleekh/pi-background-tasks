# Issue 18: Feature: opt-in auto-backgrounding for the built-in `bash` tool
Author: niksite (NONE)
State: open; Created: 2026-09-10T22:38:46Z; Updated: 2026-09-10T22:38:46Z
URL: https://github.com/ismailsaleekh/pi-background-tasks/issues/18

`bg_run` works when the agent knows in advance that a command is slow. It does not help in the common case. A test suite or an install blocks the session for ten minutes, because nobody expected it to be slow.

This proposes an opt-in mode. If a `bash` command still runs after a threshold (5s by default), the extension turns it into a normal background task. The tool returns at once. The existing completion notification wakes the agent later. Auto-backgrounded jobs then appear in `/bg`, `/jobs`, `/logs`, and `/kill`. They also get the output cap and the `timeoutSeconds` handling.

The runtime already has the primitive. `Registry.waitForEnd(task, timeoutMs)` (`src/core/registry.ts:2179`) returns `true` when the task ends, and `false` on timeout. It removes its own waiter in both cases. The flow is: call `startTask(...)`, then call `waitForEnd(task, thresholdMs)`. On `true`, return the output inline as an ordinary bash result. On `false`, return a backgrounded result.

The mode makes the package register `bash`, so the package owns a core tool instead of only adding tools. Pi resolves duplicate tool names by first registration, and it drops the loser without a message. This conflicts with `pi-tool-display` and with any other extension that registers `bash`.

I run this locally as an extension that calls the built-in bash tool and races it against the threshold. It keeps its own job files, so `/bg` and `/jobs` never see those jobs. That is why I ask whether this belongs in the package.
