# Issue 6: Feature: let background tasks survive /reload (reattach persisted tasks by pid with file-redirected output)
Author: chenyn273 (NONE)
State: open; Created: 2026-08-15T02:52:21Z; Updated: 2026-08-15T02:52:21Z
URL: https://github.com/ismailsaleekh/pi-background-tasks/issues/6

## Is your feature request related to a problem?

`/reload` is a hot-reload of configuration/extensions with **session continuity**: the conversation history and context are preserved. But background tasks are killed, which is inconsistent with that semantics — and painful for long-running work (a 20-minute test suite dies because you reloaded a config).

## Current behavior (reproduced)

Reproduction: start `pi`, create a background task (`sleep 90 && echo done`), wait for `bg 1 running` in the status bar, then run `/reload`.

Result — pi reloads cleanly (no crash, no orphan process — good!), but the task registry JSON (`.pi/tasks/session-*/<id>.json`) shows:

```json
{
  "status": "killed",
  "signal": "SIGTERM",
  "error": "Killed during Pi session shutdown/reload",
  "notified": false
}
```

So the graceful kill is clearly intentional today. This request is to reconsider that choice for the reload case.

## Why survival looks feasible

Two of the three pieces already exist:

1. **Task metadata is already persisted** (`.pi/tasks/session-*/tasks-*.json`).
2. **Output is already persisted** (the `.output` file).
3. The only things that break across reload are the child's stdout/stderr **pipes** (attached to the old extension instance) and the **in-memory registry** of the new instance.

Suggested approach — an opt-in `durable`/`detached` mode per task:

- Spawn with `detached: true` and redirect stdio **to the output file** instead of pipes (or keep pipes and additionally `tee` to the file).
- On `session_start` with `reason === "reload"` (and optionally `resume`), the new instance scans the persisted registry and **re-adopts live tasks by pid**:
  - liveness via `process.kill(pid, 0)` polling (or a periodic check),
  - output via tailing the output file,
  - completion detection via exit probing + final output read.
- Wake-ups after adoption are delivered through the new instance's own (active) ctx, so there is no stale-context risk — unlike the failure mode that motivated the kill (see trvon/pi-loop#33, where a stale-ctx emit crashed the whole pi process; the fix there was teardown, but the "cannot adopt a previous child" limitation is specific to pipe-attached children, not file-redirected ones).

## Alternatives considered

- Keep current behavior, document "stop/await your tasks before reload" — works but shifts the burden to the user for every reload.
- `nohup`-style manual workaround — loses wake-up, status, and registry integration, i.e. the whole point of the extension.

## Environment

- pi-background-tasks 2.4.2
- pi (@earendil-works/pi-coding-agent) 0.84.2, macOS, node v22.22.3
